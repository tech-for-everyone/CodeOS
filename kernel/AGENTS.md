# CodeOS AGENTS.md

Guidance for humans and coding agents working on this tree.

## Goals
- Make CodeOS feel like a daily-driver hobby OS
- Android / Linux app support (containers + Zircon)
- Keep the desktop approachable and polished

## Layout notes
- **Canonical panel apps** live in `pkgs/core/panels/src/` — the kernel Makefile
  compiles those, not the older copies under `kernel/kernel/`.
- Userspace programs are built from `pkgs/core/<name>/src/` via
  `kernel/userspace/Makefile`, then embedded with `scripts/gen_initramfs.py`.
- Kernel-injected packages use a `pkgs/core/<name>/src/KERN` marker. The
  graphics stack lives in `pkgs/core/graphics/` and is compiled into the
  kernel automatically.
- OpenWeb's HTTP backend and HTML renderer are Rust: `kernel/kernel/rust_ow/` (needs `cargo`); the renderer writes the C-owned grid globals in `qt6/panels/ow_html.{c,h}` (see the OpenWeb section below).
- **Zircon OS** (`Zircon/`) is a standalone mobile/desktop OS built on the CodeOS kernel.
  It has its own init process (`zircon_init.c`), compositor (`zircond`), and bootable ISO.
  Build: `make -C Zircon all && make -C Zircon iso`.
  Zircon uses `kernel/kernel/windows.h` for `window_t`, `kernel/kernel/gui/` for GUI types,
  and `kernel/kernel/sys/` for kernel IPC syscalls.

## Build
```sh
make -C kernel all
make -C kernel codeos-1.0.iso
make -C kernel run-iso
```
Host needs `x86_64-elf-gcc`, `xorriso`, `python3`, `cargo`, and QEMU for run targets.

## Jengine (`src/jengine.c`) — one source, two consumers, freestanding wins
- `jengine.c` is compiled into **both** the host test (`make jengine-check`, real libc) and the kernel (`SRC_C += ../src/jengine.c`, `x86_64-elf-gcc -ffreestanding -nostdlib -nodefaultlibs`). The kernel toolchain has **no libc headers at all** — `#include <stdlib.h>` is a fatal error, not a warning. So this file may not use `malloc`/`calloc`/`free`, `strdup`, `strcmp`/`strlen`, or `isalpha`/`isdigit`; it defines its own. The stricter of the two consumers sets the rule, and the host build cannot be allowed to drift into using libc.
- Verify **both**, not just the host. The kernel-side check is
  `x86_64-elf-gcc -ffreestanding -nostdlib -nodefaultlibs -Wall -Wextra -Werror -Iinclude -c src/jengine.c`.
  Afterwards `nm -u` the object: the only permitted undefined symbol is `memcpy`, which the kernel provides in `kernel/kernel/string.c` (linked as `kernel/string.o`). Anything else means a libc call crept in.
- The interpreter is fixed-size by necessity, not by preference: static scope/function tables and fixed name slots, with recursion capped at `JENGINE_MAX_DEPTH`. That is *why* values are `int64_t` only — there is no allocator, so `jengine_value.str_val` stays unused for API compatibility rather than being filled.
- `jengine_eval()` **resets interpreter state on entry**, so every evaluation is independent. This is deliberate: `jengine_init()` is called once at panel init and the calculator then evaluates every keystroke against the same engine, so leaking `let x = 5` into the next query would be a bug, not a feature.
- **jengine is currently dead code inside the kernel image.** `jengine.o` is on the link line and links cleanly, but nothing in the kernel references `jengine_eval` — the callers (`pkgs/core/panels/src/panels.cpp`, `pkgs/core/panels/src/calc.c`, `kernel/kernel/codeos_litehtml.cpp`) are *not* among the linked objects, so `--gc-sections` discards the whole thing. `x86_64-elf-nm codeos-1-kernel.bin | grep -c jengine` returns 0. Its only live consumer is the host test binary. A change here is therefore build-verified but **not** runtime-verified inside the OS; do not claim the OS runs scripts until one of those callers is actually built in.


## The pre-baked `disk.img` (shipped on the ISO, **not** self-mounting)
- `kernel/disk.img` is **built, populated and shipped on the ISO** at `/disk.img`, and `codeos-1.0.iso` depends on it, so one `make` produces both and the ISO carries the exact image the OS was tested against.
- **The copy on the ISO is inert weight — the kernel cannot mount it.** Booting `codeos-1.0.iso` on its own logs `storage: no block device found`. There is no ISO9660, El Torito or loop device anywhere in the tree, and `part_init()` only ever reads real block devices (`block_read_sectors(0, …)`), so a file inside the ISO's own filesystem is not a disk as far as the kernel is concerned. The host must attach it, which every `run-iso*` target does with `-drive file=$(LIVE_DISK_IMG),format=raw,if=ide`. Do not describe the ISO as self-contained: it *carries* the disk, and attaching it is the host's job. Real self-containment needs an ISO9660 reader plus a loop block device — a driver, not a Makefile change.
- Population uses **`mke2fs -d <dir>`**, which builds the ext2 filesystem straight from a directory tree. That replaces the old `losetup` + `mount` population, which needs root — and root is not available in the build environment. The source tree is `kernel/disk/` (`etc/hostname`, `scripts/*.script`).
- The image is **partitioned**: `parted` writes an MBR and the filesystem goes in at sector 2048 (1 MiB) as a type `0x83` Linux partition. That type is not cosmetic — `main.c` PHASE 7 only mounts partitions where `p.type == 0x83`, trying `codefs_mount()` first and falling back to `ext2_mount()`.
- **On success, `main.c` immediately runs `/scripts/test1.script` and `/scripts/complex.script` off the mounted volume.** Those two paths are hardcoded there, so the image must ship them or the mount succeeds and then silently finds nothing. The `disk-img-populate` legacy target is where this came from; it was already broken (it `cp`s `/tmp/test_hello`, which does not exist, and builds `complex.script` with `echo '...\n...'`, which writes literal `\n` because POSIX `echo` does not expand escapes).
- **`script_run_file()` needed an ext2 fallback to make any of this work**, and its absence was invisible until boot. It read through `fs_get_info()`/`fs_read()` only — the in-memory node table that `initramfs_populate()` alone fills. `ext2.c` never touches that table and `vfs.c` has no dispatch to it, so the boot-time scripts failed on every mount. It now tries `fs.c` then `ext2_read_file_path()`, which is the same order `sys_open()` already used. The shell's own `cat` still has the gap, which is why `els`/`ecat` exist as separate ext2-aware builtins. Note the call also happens *before* `fs_init()`, which `memset`s the whole node table; that ordering is still wrong on its own terms but is harmless here only because the ext2 path does not go through `fs.c`.
- **csl has no comment syntax at all** — `script.c:191` maps `/` straight to `TOK_SLASH` (division) and there is no `#` case either. A `//` comment in a `.script` file lexes as division plus identifiers and the parse fails **silently**: the build is green, `mke2fs -d` copies the text faithfully, and `debugfs -R "cat"` returns it byte for byte. Every static check passes on a script that cannot run. Keep the explanation in the commit message, not in the file.
- `disk.img` and `disk.img-legacy` are **two different images on purpose**: the pre-baked populated one, and an empty ext2 for the manual `losetup` targets. They must never share a variable — the legacy block once wrote `$(DISK_IMG) = disk.img`, so building *any* legacy target (`disk-img-format`, `disk-img-populate`, and every `run`/`run-disk`/`run-full`/`run-gpu`/`run-sb` target, which all depend on `disk.img-legacy`) overwrote the populated image with an empty one. Likewise the two size variables are `LIVE_DISK_SIZE_M` and `LEGACY_DISK_SIZE_M`, not both `DISK_SIZE_M`: `?=` only assigns when unset, so a shared name silently gave the legacy image the live one's size.
- **Verify the contents without root.** There is no `sudo`, so `mount` is unavailable; use `debugfs` against the extracted partition:
  ```sh
  dd if=kernel/disk.img of=/tmp/part.img bs=512 skip=2048 status=none
  debugfs -R "ls -l /bin" /tmp/part.img          # expect exactly len(USER_PROGS) files
  debugfs -R "cat /scripts/complex.script" /tmp/part.img
  debugfs -R "dump /bin/shell /tmp/s" /tmp/part.img && cmp /tmp/s kernel/userspace/shell
  ```
  A successful `make disk.img` is **not** evidence the filesystem was populated — a silent `cp` failure inside the recipe still exits 0. Count `/bin` against `USER_PROGS` and `cmp` a dumped binary against its source; both are cheap and catch it. To check what actually shipped inside the ISO, `xorriso -osirrox on -indev kernel/codeos-1.0.iso -extract /disk.img /tmp/from-iso.img`.
- **All of the above is still not a boot test, and two real defects got past every one of those checks.** Only the serial log settles it. Attach the disk explicitly — the ISO's own copy is not used (see above) — and assert on the marker lines:
  ```sh
  qemu-system-x86_64 -machine pc -m 1G -smp 2 -vga none -nographic -monitor none \
      -boot order=d -cdrom kernel/codeos-1.0.iso \
      -drive file=kernel/disk.img,format=raw,if=ide -no-reboot 2>&1 \
    | sed -e 's/\x1b\[[0-9;]*[A-Za-z]//g' > /tmp/boot.log
  ```
  Expect `block: ATA disk detected (129 MB, …)`, then the two scripts' own output. `codefs: bad magic … / codefs: mount failed` is **expected and harmless** on an ext2 volume — that is the fallback branch being taken, not a second fault. `script: cannot open …` is the real failure. Use `-machine pc -vga none`, not `q35` alone: without `-vga none` the kernel initialises VBE and goes graphical, and the serial log goes quiet before the storage phase.
- **Assert the fix as a pair, and re-run the revert.** Both defects here were "it is green and it is still broken", so a single passing boot proves little. Stash the change, rebuild the kernel *and* the ISO, and confirm the marker lines revert to the failure text; only then is the assertion known to be sensitive. Reverting `script.c` brings back `script: cannot open '/scripts/test1.script'` verbatim, which is what makes the passing log trustworthy.
- Only ship files something reads. The image used to write `/etc/shell.conf`, `/etc/term.conf` and `/etc/codeos.conf`; no code in the tree reads any of them, and the sources for the first two do not exist. The real convention is `/etc/hostname` (read by `zircon-info`), `/etc/users.conf`, `/etc/wifi.conf` and `/etc/locale.conf` (written by `installer_qt.c`).

## process_t: fork(), and why the kernel half must be shared (not COW'd)
- **Two schedulers, and only one of them works.** `thread_t` (kernel threads, own stacks, `sched.c`) is a real preemptive scheduler. `process_t` (userspace address spaces) has no scheduler at all: `current_process` was assigned in exactly one live place — `proc_create()`, and only when no process was current — and `sched_switch_to_process()` had **zero callers**. `SYSCALL_FORK` builds a `process_t` and returns its pid; nothing can make the child run. So `fork()` returning a pid is not evidence `fork()` works.
- **`fork()` also reset the machine, and the cause is worth remembering.** The COW clone walked *all* 512 PML4 entries and copy-on-wrote the kernel half like user pages:
  ```c
  old_pt[l] = (old_pt[l] & ~PAGE_WRITE) | PAGE_COW;   /* the LIVE parent's tables */
  ```
  For the kernel half those are the tables the CPU is using at that instant — `0xffffffff80000000` (the kernel image) is `PML4[256] -> PDPT[0] -> PD[0] -> PT[0]`. So `fork()` cleared `PAGE_WRITE` on the **running kernel's own code and data**, the next write faulted, and the fault handler's stack was in that same read-only memory: double fault into triple fault. The signature is a **silent reset with zero `PF at RIP` lines** on the serial port, and `qemu ... -no-reboot` exiting **0** (a reset), not 124 (a timeout). Kernel mappings must never be COW'd: the child now gets `new_pml4[i] = old_pml4[i]` for `i >= (phys_to_virt_base >> 39) & 0x1FF`, which also matches what `vmm_kernel_pml4()` already assumes.
- **Sharing that half obliges the reaper to skip it.** `proc_wait()`'s teardown walks and frees every present PML4 entry of the dead child. Left alone it would free the *shared* kernel page tables out from under the running kernel. It must stop at `kernel_half`. Any future "free the child's address space" code has the same obligation — free the user half, share the kernel half, and never free a table you did not allocate.
- **How to localise a silent reset.** Instrument `proc_fork()` and read the *last* trace, not the fault message — there is no fault message. Per-`i`/`j` granularity is the useful level; per-page-`k` produced 8703 lines and told you nothing. The evidence that pinned it: it completed `PML4[0..255]` and died entering `i=256 j=1`, with 209941 pages still free (ruling out PMM exhaustion), and the huge-page traces started at `pd[256][0][1]` — so `k=0`, the kernel image, had gone through the 4KB path untraced.
- **Two hypotheses that testing killed, do not reintroduce.** (1) *PMM exhaustion* — `free=209941` at the crash. (2) *The physical/virtual confusion in `proc_fork`* is real but **accidentally harmless**: `process_t::pml4` is a physical address (`vmm_current_pml4()` is `read_page_table_base()`, and `vmm_switch_pml4()` writes its argument straight into CR3), and so is `pmm_alloc_page()` (`page_to_addr()` is `page << PAGE_SHIFT`), yet the code dereferences both directly *and* wraps them in `phys_to_virt()`. That works only because the low ~1GB is identity-mapped (`phys_to_virt_base = 0xFFFF800000000000`, so `phys_to_virt(0x374000) = 0xFFFF8000400374000`). It read as a crash cause and was not one. It is still wrong to rely on: `proc_wait()` also derefs `child->pml4[pt]` raw and calls `virt_to_phys()` on a CR3 value.
- **Booting Zircon to test any of this needs a framebuffer.** `main.c` gates the launch on `if (boot_zircon_init[0] && has_fb)`, so `-vga none` silently skips Zircon init entirely and drops you into the CodeOS shell at `root#` — which looks like a Zircon failure and is not one. Use `-vga std -display none -serial stdio`. Also note `PML4_SHIFT` is private to `vmm.c`; there is no shared header constant for it.
- **After the fix, `fork()` returns and nothing more.** `zircon: compositor launched (PID 4)` prints and the machine then sits idle: the child exists but no `process_t` scheduler exists to run it. Syscalls are the LSTAR `syscall` instruction, not `int 0x80`, and `syscall_entry` switches to a single **global** `syscall_kernel_rsp`, so all processes share one syscall stack — a switch has to swap that global, which is why `process_t` now carries `kstack_top`.

## ncvm: host test harness (`pkgs/core/ncvm/tests/`)
- `make ncvm-check` (also wired into `make check`) builds a host test binary by compiling the **real** `ncvm.c` with `main` renamed (`#define main ncvm_main`), including it from `ncvm_test.c`, and shadowing `kernel/userspace/include/unistd.h` with `codeos_shim.h` which maps every syscall onto POSIX.
- The shim models the **contract, not convenience**: CodeOS open flags are the Linux values (O_WRONLY=1, O_RDWR=2, O_CREAT=0x40, O_TRUNC=0x200), so they pass straight to POSIX `open()` — a missing `O_CREAT` fails in the harness exactly as in the guest. This is how the `write_file` bug (discarding the fd, calling stdout-only `sys_write`) was visible in the host tests.
- `sys_readdir` contract in the shim matches what both callers already assumed (NUL-packed names, byte count returned). Only two consumers exist: `ncvm.c` (3 sites) and `crosvm-launcher.c` (1 site).
- Lifecycle tests fork real children: one traps signals (the VMM stand-in), one deliberately does not (the supervisor stand-in). Signalling the wrong one is visible as a missing marker line and a dead supervisor. pause/resume are asserted through `/proc/<pid>/stat` ('T' vs 'S'), because SIGSTOP cannot be caught and a non-traced child produces no "continued" wait report on Linux.
- **Negative controls are mandatory.** The lifecycle tests were validated by reverting only the signal target to the supervisor pid and confirming 4 of 113 checks fail. The readdir test planted its sentinel *outside* `CMD_DIR` (`CMD_DIR/../victim.cmd`), so a traversal bug would reach it — not inside where `..` cannot escape.
- Run: `make ncvm-check` (also part of `make check`).

## ncvm: sys_readdir contract (kernel + userspace)
- **Contract**: the buffer is filled with NUL-separated entry names, packed (no fixed-stride padding). `max_bytes` is the byte capacity of the caller's buffer. The return value is the number of bytes written (i.e. the caller's loop bound), or <= 0 on error.
- Previously `sys_readdir` copied a fixed-stride `names[count][FS_NAME_MAX]` array and returned the *entry count*. Every caller treated that count as a byte length, so a directory of 10 files reported 10 and the caller walked 10 bytes of a 320-byte buffer — only the first ~4 entries were seen and the padding was uninitialised stack. `crosvm-launcher.c:300` even had a comment asserting the opposite of the truth.
- Fixed by delegating to `fs_dir_list()` (the single canonical lister already used by `vm_manager.c`), which writes packed NUL-separated names. `kernel/userspace/include/unistd.h` updated with a doc comment stating the contract. Both live consumers (`ncvm.c` and `crosvm-launcher.c`) already walked the buffer the packed way; the kernel now honours it.
- End-to-end verification: `ncvm --selftest` plants 8 known names in `CMD_DIR`, requires all 8 back intact, asserts the byte count equals the packed length, and confirms the walk lands on the end without reading past it. Boot evidence:
```
ncvm: selftest readdir 8 of 8 planted names in 65 bytes
ncvm: selftest [ok  ] sys_readdir returns every name whole, not just the first few
ncvm: selftest [ok  ] the listing is packed NUL-separated names, not fixed-stride records
```

## Task security levels (systemm is the authority)
- Every task carries a level, ordered by privilege. **A task may act on anything at or below its own level, never above** — the ordering *is* the permission model, there is no separate ACL:
  - `0` container — containerized env, potentially dangerous
  - `1` os — run by the actual OS, still high security
  - `2` user — most programs; hyperde → systemm → kernel
  - `3` kernel — kernel apps: apphost (X11/window protocol), zircon, container initializers
- `kernel/kernel/systemm.{c,h}` is the **single authority**. It answers with the level as a plain number (`systemm_level_of()` → 0..3, or -1 for no such task) and enforces the rule (`systemm_may_act()`, `systemm_kill()`, `systemm_set_level()`). The `systemm task` shell builtin calls into it rather than deciding for itself, and the three kill syscalls (KILL 62, TGKILL 234, `SYSCALL_KILL` 51) funnel through one `gated_kill()` in `syscall.c`. **Enforcement is in the syscall path, not the builtin** — before that, a program could call `kill(2)` and skip the check entirely. `proc_can_interfere()` was deleted for being a second copy of the rule; do not add another.
- The caller's level comes from `current_process`, never from a syscall argument, so it cannot be forged. That is only sound because of a scheduler invariant: `sched_timer_tick()` clears `current_process` only in a branch that already requires `need_resched`, and `isr_dispatch_c()` acts on `need_resched` by `sched_yield()`ing before returning to user mode. Break that and `systemm_caller_level()` returns -1 and everything denies (fail-closed).
- Refusals are `-EPERM`, a missing pid is `-ESRCH` — different answers, because a caller may act on them differently. `proc_get_level()` returns `LEVEL_KERNEL` for an unreachable pid so a nonexistent target can never be mistaken for a low-privilege one that is free to kill.
- Seed levels: a **container initializer** (`container_start()`) is `LEVEL_KERNEL`; the **apps inside it** (`container_exec()`) are `LEVEL_CONTAINER` whatever asked. The initializer is the trusted part that sets up namespaces/cgroup/uid mapping and launches the untrusted payload. `container_exec()` also demotes to `LEVEL_CONTAINER` on the `host_mode` branch, where `proc_exec()` reuses the caller's `process_t` — without that, a level-2 user could ask to run inside a container, keep level 2, and signal level-2 *host* processes from in there.
- `systemm task list|info|level|set|kill|run`; `task level <pid>` prints just the number for scripting. `ps` shows levels. `proc_list()` lives in `systemm.c` because `process.c` is the layer below and cannot call back up, so the level-name table could not otherwise be shared.
- Test with `/bin/leveltest` (`pkgs/core/leveltest/`), which calls `sys_kill(pid, 0)` the way any program would — signal 0 does the permission check and delivers nothing. `leveltest --into <id> <path>` re-execs through the container-exec syscall, which is the only way to reach the `host_mode` branch.
 - **Level-gating audit (2026-09):** previously only `gated_kill()` enforced the model. Added `level_gate(LEVEL_KERNEL)` in `syscall.c` for all container/VM state-changing syscalls: `SYSCALL_CONTAINER_CREATE|START|DESTROY`, `VM_CMD_CREATE|START|STOP|DESTROY|PAUSE|RESUME`, `VM_CMD_CONTAINER_START|STOP`. `level_gate` returns `-LINUX_EPERM` if the caller's level is below `required_level`; a caller with no `process_t` (kernel context — waydroid, android session, VM boot) keeps full authority. All container/VM ops now require `LEVEL_KERNEL`. **Verified at runtime**, not just built: `/bin/leveltest --gate <name>` at level 2 returns -1 with no container created, while with `level_gate` neutered the same run returns container id 1. See the traps below before writing another test here.
 - **`level_gate` only guards the syscall path, and that is by design — but know it.** The shell's `appvm`/`container` builtins call `container_create()` and friends *directly* (`shell.c:2368` and following), so they never reach the dispatcher and are not gated. That is why the level-2 shell can still build containers, and why it is the right **control** for the gate test: same binary, same image, same moment, the only variable being syscall-vs-direct.
 - **A level-3 process cannot be obtained from the shell, so don't try to use one as a control.** `shell_level` is `LEVEL_USER`, and `systemm task run --level 3` is refused with "level 2 (user) may not start a task at level 3 (kernel)". That refusal is the anti-escalation rule working correctly.
 - **`sys_container_list()` is useless for checking whether a container was *created*.** It calls `container_list()`, which returns only `CONTAINER_RUNNING` entries, so a created-but-never-started container is invisible by design. A test that creates a container and then looks for it by name reports "absent" even when creation plainly succeeded — which is how the first version of the `--gate` check managed to report "REFUSED" against a completely disabled gate. Use the return value: `container_create()` returns the new id on success, and there is no other way to get a positive one.
 - **A negative result is not proof of a refusal.** `-1` is also what "already exists", "no slots available" and "unknown image" return, so a lone -1 is equally consistent with a wide-open gate and a broken image path. Pair every such assertion with the builtin control.
- **Dropping into user mode needs a *named* return leaf, never a C return address and never a private syscall stack.** `user_mode_enter()` records `(%rsp)` as the return target unless `user_mode_set_return()` named a leaf, and `user_mode_force_return()` is a bare `jmp` to it. Both container entry points are execs (`proc_exec()` replaced the process's program), so the syscall or builtin that asked is never resumed:
  - Kernel-context callers (`appvm run`/`appvm exec` from the shell) have a **live** C frame, so the leaf returns into it and the shell carries on. `container_exec_done` handles this by just calling `shell_exec_done()`.
  - The container-exec **syscall** caller is a real process whose frame is **dead**. Returning into it popped a return address off a stack that had already been freed and faulted — user mode, `cs=0x23`, a garbage RIP. The leaf instead does `user_mode_restore()` + `user_mode_force_return()`, which unwinds exactly one exec level onto the enclosing (still-live) shell frame. `user_mode_restore()` only restores *globals*; it does not touch the live `%rsp`, so the unwind has to go through `user_mode_force_return()`.
  - `syscall_kernel_rsp` must point at the process's own `syscall_stack_top` (sized `SYSCALL_STACK_SIZE` by `alloc_syscall_stack()`), like `SYSCALL_EXECVE` does. It used to be a private `pmm_alloc_page()` — one 4 KiB page, which `umode_entry.S` already documents as overflowing into adjacent user pages — and it was freed on the way out while the live trapframe still stood on it, and leaked outright in the kernel-context branch that returned before the free.
  - The unwind flag must be captured **before** the `proc_create` branch, which reassigns the local and would make the test unconditionally true — which sends the leaf to a stale `user_mode_return_rip` (observed as a jump to address `0x3`).
- `user_wm_release()` has exactly one caller, in the container-exec leaf. It used to sit on the abandoned return path, so the android window bridge was never actually released; it now runs in the leaf before the unwind.

## Waydroid (Android on the desktop, kernel shell builtin)
- `waydroid` is a kernel shell builtin (`cmd_waydroid` in `kernel/kernel/waydroid.c`). Flows: `waydroid init` (idempotent — the `android-stock` image ships complete at boot, including `build.prop` and all 10 apps under `<image>/system/app/<name>/<name>`); `session start|stop|pause|resume` drives the appvm container; `app list|launch <app>`; `shell` runs `/bin/sh` in the guest; `status` reports image/root/session/gui.
- Apps are userspace ELFs in `pkgs/core/<name>/src/`, built into `/bin/android-*` via `kernel/userspace/Makefile` (`ANDROID_PROGS` + `LIB_ANDROID` = `lib/android_ui.o`) and embedded by `gen_initramfs.py`; the `android-stock` image is populated at boot from those ELFs by `rootfs_seed_android_stock()` (`kernel/kernel/rootfs.c`), and apps are launched inside the container via `container_exec(id, "/system/app/<name>/<name>")`. The app-name list is the single source of truth `rootfs_android_apps` in `rootfs.{c,h}` (shared by rootfs seed + waydroid UI).
- `appvm`/`container` shell commands work directly on the seeded image: `appvm images` enumerates `/containers/images/`, `appvm pull <debian-minimal|android-stock>` materializes an image, and `appvm run <image> <cmd...>` is docker-style — it activates the fresh container (`container_mark_running`) and execs the command directly (no entrypoint boot), then removes the temporary container on exit; `appvm run <image>` without a cmd boots the entrypoint and keeps the container running.
- **User-window bridge** (`kernel/kernel/user_wm.{c,h}`): maps WM-protocol messages on fd 3 (commands) / fd 4 (events) to LVGL desktop windows, with fds/events wired in `syscall.c` (READ/PWRITE hooks, `UW_FD_EVT=4`/`UW_FD_CMD=3`) and input/tick routed from the compositor thread in `lvgl_port.c`. `container_exec` calls `user_wm_setup/release` for `/system/app/*` paths; `main.c` arms the bridge via `user_wm_init()` when a framebuffer is present.
- When the bridge/desktop is absent (headless boot), apps self-report and fall back to console mode — this keeps `make -C kernel codeos-1.0.iso` + headless QEMU (`-vga none -nographic`) verification deterministic: `waydroid app launch android-calculator` boots the app and its console REPL evaluates expressions.
- Note: kernel `snprintf` has no `-` flag (right-align with the widest width instead) and `fs_resolve()` returns the node index — test with `>= 0`, never `== 0`.

## OpenWeb (litebrowser-style lightweight browser)
- Two Rust halves, one C contract: the **HTTP/tab backend** (`kernel/kernel/rust_ow/src/lib.rs`, built into `libow_http.a`) owns the tab array and fetching; the **HTML renderer** (`kernel/kernel/rust_ow/src/ow_render.rs`) is a direct Rust port of the old C `render_html()` and is exported as `ow_render_rs(const char *html, int len)`.
- The renderer writes the **C-owned output globals** declared in `qt6/panels/ow_html.h` (`ow_txt[512][120]`, `ow_txt_lines`, `ow_line_info`, `ow_links`, `ow_images`, `ow_forms`, `ow_form_fields`, `ow_page_title`, `ow_need_render`, …) through `extern static`, so the Qt frontend (`qt_panels_openweb.cpp`) and `openweb_core.c` are unchanged. `qt6/panels/ow_html.c` keeps only those globals, the parallel image workers + `ow_image_download()`, and the exported form API (`ow_field_set_value/toggle/at`, `ow_form_build_query`).
- The persistent **form edit cache** stays in C (identity keys name+type+form-action) because it is re-applied on every re-render; Rust calls the thin `ow_fv_restore(ow_form_field_t*, int)` / `ow_fv_store(const ow_form_field_t*, int)` bridges instead of duplicating the logic.
- `openweb_tab_t` in `pkgs/core/panels/src/ow_http.h` must mirror the trailing `_redirect_depth` field of the Rust `OpenwebTab` struct — without it the C and Rust `sizeof` differ and tab indexing past 0 is broken.
- **WebView-style navigation API** lives in the Rust core, so every frontend shares one history: per-tab back/forward stacks (`ow_go_back()`, `ow_go_forward()`, `can_go_back`/`can_go_forward` fields, filled from the stacks), `ow_stop_loading()` (best-effort — fetches are synchronous, so the flag is polled between redirect/retry iterations), and per-tab URL recording on `ow_navigate`/`ow_search`/`ow_navigate_post`/`ow_tab_new`. History is stored in `HIST_URL`/`HIST_LEN`/`HIST_POS` statics (32 entries × 256 bytes per tab) and shifted together with `TABS` in `ow_tab_close()`. This mirrors the webkit6 `WebView` API (`go_back`/`go_forward`/`reload`/`stop_loading`/`can_go_back`/`can_go_forward`/`estimated-load-progress`) so a future GTK4 or Zircon frontend can port the demo `WebView` browser directly; `openweb_core.c` exposes the same through `ow_core_back/forward/stop/can_go_*`, and the userspace tty app gets them as `sys_web_go_back/forward/stop` (`WEB_GO_BACK=11`, `WEB_GO_FORWARD=12`, `WEB_STOP_LOADING=13`).
- Note: the desktop Qt panel keeps its own per-tab C++ history (`m_hist`/`m_histPos`) for back/forward button state — it is a display layer on top of the same backend, not a second source of truth for the other frontends.
- **tty app single-key hotkeys need `TCSETS`, and `TCGETS` was broken for every app.** The serial input path is canonical by construction: `sys_read()`/`kernel_read()` on fd 0 spin on `serial_readchar()` until `\n`/`\r`, so the tty `openweb` app's `b`/`f`/`s` hotkeys could not fire until an Enter followed each one. `ioctl` now implements `TCSETS`/`TCSETSW`/`TCSETSF` (0x5402-4) alongside the existing `TCGETS`; clearing `ICANON` in `c_lflag` (offset 12 of the 44-byte x86-64 `struct termios`) makes both read paths return keystrokes as they arrive. `TCGETS` reports `ICANON` according to the mode actually in force so the usual `tcgetattr`→tweak→`tcsetattr` round trip works. Only `c_lflag`/`ICANON` is interpreted — the serial input path does no echoing and has no signal or flow-control handling, so `ECHO`/`ISIG` are accepted and ignored.
- **The tty mode is `process_t::tty_raw`, deliberately not a global.** fd 0 is shared by every process, so a global would let an app that exits in raw mode strand the shell in raw mode with no line buffering and no way to type a command. Per-process means the flag dies with the process; the app still restores on exit as hygiene. `cmd_exec` uses `proc_create()`, so the app gets its own `process_t` rather than sharing the shell's.
- **The console fds must bypass `FD_CHECK` in the `LINUX_IOCTL` case.** `fd_table` is only populated by `fd_alloc()` on the Linux-compat `open` path; `proc_create()` registers nothing, and `sys_read`/`sys_write` special-case fd 0-2 without consulting `fd_table`. Gating the ioctl on `FD_CHECK` therefore rejected the console for exactly the programs that want to set the terminal mode — `tcgetattr` returned `-EINVAL` and the app silently stayed in canonical mode. Accept fd 0/1/2 directly, as the read/write paths do.
- `ioctl` is a Linux-compat syscall, so it is only reachable under `PERSONALITY_LINUX`; setting that personality permanently would divert the app's CodeOS-native syscalls (including `SYSCALL_WEB`) into the Linux translation table and break them. `sys_ioctl_linux()` in `kernel/userspace/include/unistd.h` sets the personality for the one call and restores it, and the app calls only `tcgetattr`/`tcsetattr` from there. There is no syscall to read the personality back, so the restore assumes native `0` — correct for the openweb app, but a process that lives under `PERSONALITY_LINUX` (`linux-runner`, `crosvm-launcher`) must not use these helpers.
- Hotkeys still shadow URL text entry: `handle_key()` tests the hotkeys before the printable-character fallthrough, so typing a URL like `http://…` triggers `h`/`t`/`p` first. The help text's "Type to enter URL" is therefore only true for characters that are not hotkeys. Fixing this needs a mode toggle (a key that suspends hotkeys while a URL is typed) — a UX decision, not a bug fix.
- Headless verification: `ow render <url>` (shell builtin in `shell.c`, weak-linked to `ow_core_navigate()` + `ow_core_dump_active()` in `openweb_core.c`) fetches the page with the Rust backend, renders with `ow_render_rs`, and dumps the text grid + links + fields to the console. `ow state` prints `can_go_back`/`can_go_forward`/`load_progress`, and `ow back`/`ow forward`/`ow stop` drive the navigation API from the shell — all pure getters or the same core calls the frontends make, so they need no network of their own. Host a page with `python3 -m http.server 8000 --bind 0.0.0.0`, then boot the ISO with `-vga none -nographic -monitor none -netdev user,id=net0 -device e1000,netdev=net0` and run `ow render http://10.0.2.2:8000/test.html`.
- **`cache_lookup`/`cache_store` must be given a NUL-bounded slice, never a whole buffer.** `CACHE_URL` is `[u8; OW_URL_MAX]`, and both functions probe `CACHE_URL[i][url.len()]` to confirm the stored key is NUL-terminated. Handing them `&final_url` (the full 512-byte array) made that index 512 — one past the end — and the `CACHE_URL[i][..].len() >= url.len()` guard written to catch it was a tautology (`512 >= 512`), so it caught nothing. With `panic = "abort"` and a silent `loop {}` panic handler the result was an unreported system-wide hang, not a crash. Both now reject `url.len() >= OW_URL_MAX` and are called with `&final_url[..strlen_u8(&final_url) + 1]`; the same slicing is applied in `ow_go_back`/`ow_go_forward`, where `buf_as_str()` UTF-8-validates the *whole* slice and so would otherwise read stale bytes past the NUL and silently misclassify a URL as a search query.
- A Rust panic here prints `OWPANIC: <file>:<line>` on COM1 before spinning. The previous handler was a bare `loop {}`, which is indistinguishable from a hang or a wedged scheduler — always check for that line when OpenWeb stops responding. Note COM1 is a *port* (`in`/`out`), not memory-mapped: dereferencing `0x3F8` faults with `CR2=0x3fd`.
- The full CSS/`litehtml` layout engine is **not** wired up yet (the upstream `litebrowser-linux` `litehtml` submodule is empty); rendering is the text-grid engine above. `libow_http.a` has no Make prerequisites if the rule is left bare — `kernel/Makefile`'s `RUST_LIB` rule depends on `kernel/kernel/rust_ow/src/*.rs` + `Cargo.toml`.

## Desktop chrome, and verifying it (screenshot harness)
- The window decorations follow macOS, not COSMIC: close/minimize/zoom sit on the **left** of the title band in that order, the title is **left-aligned** after them, and an unfocused window's lights go grey (`#5A5A5E`) rather than being alpha-dimmed. `draw_window_chrome()` in `hyperde/src/lib.rs` is the authoritative painter; `QtAppWindow::paintEvent` mirrors it because the compositor's pass repaints the whole band on top of whatever Qt drew, and its hit rects are recomputed in `paintEvent` so the hit-test cannot drift from the paint.
- The Qt inset is `sh+14`, **not** `cr+sh+14`: the rounded corners are applied *inside* the band, not by insetting from it, so adding `cr` pushes the Qt hit rects 12px right of the lights the compositor actually draws.
- `render_bar` and `hyperde_shell_bar_hit()` share one layout by hand and must be changed in lockstep — the hit-test mirrors the paint coordinate-for-coordinate. Same for the Qt strip's `mousePressEvent`, which delegates to it.
- **A visual change with no screenshot is unverifiable.** `kernel/scripts/shot.py` boots the ISO headless with `-vga std -display none` and drives a QMP socket (`key`/`click`/`move_rel`/`goto`/`screendump`); `shot_probe.py` decodes the PNG and locates the traffic lights; `chrome_check.py` asserts the chrome arrangement against pixels; `chrome_scan.py` reports where lights actually are, frame by frame, which is the diagnostic when a check fails.
- **Window rects must be read from the compositor's own log, never guessed from the framebuffer.** The title text, app icon and focus ring all break a run of band colour, so any "how far from the edge" measured that way is really a measurement of the title. The log is `PRS pos xid=N 'Title' @x,y WxH` for X11 and `HYPERDE: tile SYNC ws=W id=N ... '@x,y WxH' title='T'` for Qt — and it must be the **`tile SYNC`** line, not `tile RUN`, which prints `sr=`, the *screen* rect the tiling was computed from. Keep the **last** rect per window id; the demo compositor re-tiles each window several times, and a stale rect makes the check look for lights in empty space.
- The desktop double-buffers and composites progressively: two boots of the same ISO produced byte-identical serial logs and screenshots that disagreed completely, and an intermediate frame carries *one* window's chrome and none of the others. So a check must **drive its own capture loop and accept only a frame that passes** — "the frame has some dots" is not a pass criterion. In practice it took 6–32 captures to get a usable frame.
- `chrome_check.py` reports a window as `[skip]` when another window's title band provably covers its lights, and still exits non-zero if that leaves nothing judged. A silently skipped check is how a gate starts passing for the wrong reason. The Qt family was previously always skipped because penrose tiles the demo windows (HyperDE, DevStore, OpenWeb) to fill the screen, covering the Qt lights.
- **`no-demos` is the boot flag that makes the Qt family measurable**, via the limine entry `CodeOS (No Demos)` (entry 4) or `shot.py --boot-entry 4`. `main.c` sets it from the cmdline, `penrose_bridge.c` holds it, and `penrose_init()` in `rust_penrose/src/codeos.rs` skips the spawn loop. Note the live spawner is the **Rust** side: `prs_demo_spawn()` in `penrose_bridge.c` is a dead C leftover with no callers anywhere, and its symbol is absent from the linked binary. Verified: 6 `PRS pos` lines with demos, 0 with the flag, and the Qt check then passes — `PASS qt:'Terminal' @(8,36) 1264x676 band y=57 dots at x=28,48,68 -> close/min/max` — on the **first** capture rather than needing 6–32 retries.
- **The No Demos entry repeats `httpsboot` from the default entry deliberately.** It must differ from the default by `no-demos` and nothing else, or the comparison is confounded — see the `httpsboot` bug below, which is exactly the trap that cost an hour here: an early version of this entry omitted `httpsboot`, the desktop page-faulted, and the fault looked like it belonged to the new flag.
- **`chrome_check.py --no-demos` asserts the boot entry from the serial log rather than assuming it.** The menu keys are timed against limine's `timeout:` window, so if they land before the menu is up, limine silently boots `default_entry` and the demos come back — and a check that then measures demo windows while claiming to have booted without them is precisely the silent-wrong-reason failure this script exists to catch. It fails hard if the `no-demos` line is absent or if any of the three demo titles still appears.
- **UNFIXED BUG (found 2026-09-27): the Qt desktop page-faults unless `httpsboot` is on the kernel command line.** `main.c` calls `https_boot_test()` at the end of PHASE 9, immediately before PHASE 10 launches the desktop, and only when `g_https_boot_test` is set. With it unset, the desktop dies with `!!! PF at RIP=0xffffffff80efd7a5 CR2=0x0` — a null deref inside Qt's `QResourceRoot::findNode`, immediately after `Qt6 Desktop: init`, with `rdi=0x0` and `rax=0xfefefefefefefefe` (an uninitialised-memory poison pattern). `HYPERDE: render` then never happens, because the compositor wedges first.
  - This is **not** a timing race and **not** caused by `no-demos`. Substituting a bare busy-wait of ~0.8s — longer than the httpsboot phase itself, per the `userspace ok` phase marker going 0.309s → 1.115s — left the fault exactly where it was. So `https_boot_test()` is doing something load-bearing for Qt's resource tree, and the real bug is an init-order/registration problem in the Qt bring-up that the network test happens to paper over.
  - Correlation is 9/9 across every boot captured, with no exceptions: every boot with `httpsboot` (3/3) is clean, every boot without it (6/6) faults.
  - **Two shipped boot entries are affected.** `CodeOS (Recovery)` and `CodeOS (Safe Mode)` both use `cmdline: loglevel=4 recovery` / `loglevel=4 safemode` with no `httpsboot`, and both were confirmed to fault at the same RIP. Only the default entry works.
  - Do **not** "fix" this by adding `httpsboot` to those two cmdlines. That runs a network TLS test in recovery and safe mode, which is wrong for both, and it hides the underlying init-order bug rather than removing it. The fix belongs in whatever Qt resource registration `https_boot_test()` ends up triggering incidentally.
- **The desktop has no working mouse.** The USB HID branch hardcodes `x=0, y=0` and reports only deltas (`kernel/drivers/input.c:160`), and `kernel/drivers/ps2.c` is keyboard-only (it enables the aux port but never assembles a packet), so a synthesised click lands nowhere and hit-testing cannot be exercised. Use the keyboard: `meta_l+ret` → `launchApp(0)`, `meta_l+t` → `toggleAutoTiling()`, `meta_l+space` → `toggleLauncher()`. Note `meta_l+1..9` switches workspace and does **not** launch an app, and `launchApp` cases 0 and 5 are gated on `m_terminal`/`m_fileManager` being non-null.
- `DRAWS` counts **bar** redraws, not frames — it is only incremented inside the bar's dirty-gate. Don't use it as a frame counter when instrumenting the compositor.

## LGame (`pkgs/core/panels/src/lgame.{c,h}`) — a 2D framework whose API is mostly not in the binary
- **Most of the API is dead code inside the kernel image, the same trap as jengine.** The two games (`lgame_pong.c`, `lgame_snake.c`) use only the rect, pixel and text primitives, so `--gc-sections` discarded the entire texture path: `x86_64-elf-nm codeos-1-kernel.bin | grep -c lgame_create_texture` returned **0**, and so did `lgame_draw_texture` and every region/flipped/tinted blit. `fb_putpixel` was absent for the same reason. A defect in code no binary contains cannot be runtime-verified, so a fix to it is only **build**-verified — say so, or add a caller.
- **`lgame-selftest` exists to give that path a caller.** It draws a fixed frame whose probe pixels have exactly computable colours, and `scripts/lgame_check.py selftest` asserts them. The texture is an alpha **ramp** (opaque white at x=0 → transparent at x=63) rather than one flat colour, so the blend formula is checked across every alpha instead of at a single lucky value. The check states the formula (`blend_expect`) rather than hardcoding expected pixels, so a wrong formula makes the check fail instead of agreeing with a wrong implementation.
- **The graphical games are top-level builtins, not `games <name>`.** `games` with no recognised subcommand prints a directory listing of the six *csl text* games (`guess`, `mines`, `hangman`, `rps`, `math`, `reflex`) and returns — so `games pong` starts nothing and looks like a failure. The real commands are bare `pong` and `snake` (the `strcmp(cmd, "pong")` arm in `shell.c`). The banner advertises only `games/gplay`, so the two graphical titles are effectively undiscoverable.
- **`cmd_lgame_game` uses `strcmp(argv[0], "pong")` where `argv[0][0] == 'p'` read as a live bug. It was not.** `cmd_lgame_game` has exactly two callers, and both are full `strcmp` arms in `run_builtin` — so `argv[0]` can only ever be `"pong"` or `"snake"`, and the first-character test was already correct. The first draft of this note claimed `ps`, `pkg` and `printenv` all launched pong; `scripts/lgame_dispatch_check.py` was written to prove it, and the negative control (restoring `argv[0][0] == 'p'`) **passed**, which is what disproved the claim. The test is kept because the `strcmp` form is what survives a third caller being added later, and the check is a genuine regression guard for that — but it guards a hypothetical, so do not describe it as a bug fix.
- **`lgame_check.py pong` passing is not evidence about dispatch.** `pong` starts with `p`, so it launches pong under either implementation. A check that cannot fail is worse than none, which is why the dispatch check is a separate serial-only script: it asserts that `ps`/`pkg`/`printenv` leave the shell alone and `snake` does take over, using `lgame: fullscreen mode` (printed immediately before the dispatch, and never returning while a game runs) as the marker.
- **Booting a graphical OS cannot reach the shell**, so there is no way to run a fullscreen builtin: `main.c` calls `qt_desktop_run()`, which does not return. The `no-desktop` cmdline flag (limine entry 5, `CodeOS (Shell + Framebuffer)`) skips the desktop and the compositor, finishes the bootsplash, and drops to the shell with the framebuffer still up. Like the No Demos entry, it repeats `httpsboot` deliberately, so a framebuffer fault cannot be misattributed to the flag.
- **`lgame_check.py` needs a bidirectional serial.** `shot.py` uses `-serial file:`, which is write-only from the guest: it can watch the shell but never type into it, and the games *are* builtins. The check uses `-serial unix:...,server,nowait` and confirms both that the requested limine entry ran and that the game reached its draw path, from the serial log, before it trusts a pixel — the same "did the thing I asked for actually happen" rule `chrome_check.py` follows.
- **Sample the colours the games actually request, and read `lgame_color_hex` before trusting your own arithmetic.** `draw_game()` clears with `lgame_color_hex(0x001122FF)`, where the trailing `FF` is the **blue** byte, not alpha: `r=(h>>16) g=(h>>8) b=h&0xFF a=h>>24`, so this is r=`0x11` g=`0x22` b=`0xFF` a=`0`→255, i.e. **`rgb(17,34,255)`**. Reading it as `0x001122` and expecting `rgb(0,17,34)` is wrong. That mistake cost a run here and briefly looked like a red/blue channel swap in the framebuffer — there is none: `shot_probe.py` matches the traffic lights by plain RGB value on this same buffer, and `FG_CYAN = 0xFF00D4FF` in `shell.c` is a warm orange by design. Every other probe colour (cyan, magenta, grey) has R==B and so could never have detected a channel-order error; the clear colour is the only asymmetric one, which is why it is the one worth asserting.
- **The blend dropped the alpha channel and divided by 256.** All three blitters computed `... >> 8` and wrote `rb | g`, emitting an alpha byte of 0. The framebuffer is opaque, so nothing noticed — but `lgame_create_texture_from_screen` reads the framebuffer into a texture, and a round-trip would have read every pixel back as fully transparent. It is one `lgame_blend_pixel()` helper now, shared by all three call sites, so they cannot drift apart again — which is exactly how `lgame_draw_texture` came to use `pitch = fw` while its five siblings used `fb_get_pitch() / 4`. That one is **latent, not live**: `-vga std` gives 1280x800 (`vbe: EDID detected screen resolution of 1280x800`, mode `0x17a`) and the boot log prints `xserver: compositor screen 1280x800 stride=5120`, so `pitch/4 == width` and the two agree. It would break on a padded mode. `>> 8` was also the *wrong shift for these masks* independently: `src & 0x00FF00` already sits in the green slot, so shifting it right by 8 drops green into the blue slot — 50% white over blue came out `rgb(190,255,255)`, not `rgb(127,127,255)`.
- **`lgame_draw_texture_tinted` mutated its own source.** It scaled each texel in place, wrote it back through `tex->pixels`, and then drew the texture — so a *draw* call permanently altered it, and drawing one sprite twice with different tints gave two different pictures with no way back short of recreating the texture. It blends a local copy into the back buffer now.
- **Both renderer fixes were negative-controlled, and the sensitivity is the point.** Reverting `lgame_blend_pixel()` to `>> 8` fails **exactly** the three mid-alpha ramp probes; the opaque and transparent columns still pass, because the old code short-circuited those two — a check that failed there too would have been too blunt to trust. Reinstating the tint's in-place write-back, with the blend left untouched so block C is unaffected, fails all six G assertions plus D and E (both drawn after the mutation) and leaves A, B, C and F passing. Note what that says: **B cannot detect the mutation at all**, because B is already on screen before C is drawn — which is why the selftest needs a block G that redraws the texture untinted *after* the tint. A first draft of the comments claimed B would catch it; it would not.
- **`lgame_draw_text_scaled` clipped only the bottom edge.** The guard was `if ((uint32_t)(y + row*scale) >= fh) continue;` — no `< 0` test, and the inner loop recomputed the same row as `uint32_t py` before indexing `buf[py * pitch + qx]`. A negative `y` made the cast wrap, which happened to skip every row (so the text vanished rather than corrupting memory), but the arithmetic that would have wrapped was one branch away from being reached. Clipping is done in signed space on both edges now.
- **The game loop had no frame limiter**, so it redrew the same scene as fast as the blit allowed and pegged a core; `dt_ms` was clamped at 1000 ms, which let a one-second hitch fling the ball off the pitch. `lgame_frame_begin()` now sleeps off the remainder of a 60 FPS budget with `timer_sleep_ms()` (which `hlt`s rather than spins) and only when the frame came in under budget, and the clamp is 100 ms.
- The model cannot view images, so all visual verification is programmatic pixel assertion. Kernel `snprintf` has no `-` flag; `fs_resolve()` returns an index — test `>= 0`, never `== 0`. A Rust panic prints `OWPANIC: <file>:<line>` on COM1, which is a *port* (`in`/`out`), not memory-mapped.

## LGame 3D: fixed point, and the four bugs that counter-checking caught
- **16.16 fixed point, not float, and the reason is in the Makefile.** The kernel builds `-mno-sse -mno-sse2`, so there is no float ABI to lean on. It also makes frames bit-reproducible, which is what lets a pixel check state exact expected values instead of a tolerance around rounding noise.
- **The `lgame_3d_*` path was dead code until the selftest called it, exactly like the texture path.** With no caller, `--gc-sections` dropped the whole module — `x86_64-elf-nm codeos-1-kernel.bin | grep -c lgame_3d_begin` returned **0**, and the build was clean the entire time. `selftest_3d()` is what gives it a caller; check the symbol count in the *linked binary*, not the object, before claiming anything about it.
- **A depth scale derived from the focal length silently disables occlusion.** The original was `depth = (invz * (focal << 16) / NEAR) >> 16`, and with `focal = 360` and `NEAR = 1.0` every depth saturated at `0xFFFF`, so every pixel compared equal and the depth buffer tested *nothing*. It did not crash or look obviously wrong. The scale is now the constant `(1 << LGAME_3D_DEPTH_BITS) - 1`, valid because `lgame_3d_tri()` clips against `NEAR == LGAME_FP_ONE` before projecting, so `invz` is bounded by `LGAME_FP_ONE` by construction.
- **`lgame_fp_isqrt` had two bugs that partly cancelled, which is why it looked right.** It returned `sqrt(mag)` where a 16.16 input needs `sqrt(mag) * 256`; and its Newton seed was 128x too large, so `mag/x` truncated to 0 and eight iterations of `x = (x + 0)/2` merely halved the seed. The net error was only 2x, and 2x on a *unit* vector is invisible until the projection is used. Replaced with the digit-by-digit restoring sqrt, which has no seed and cannot stop early. Note the trap: `normalize()` dividing by 2x-too-small still yields a vector pointing the right way, so a spot-check of direction says nothing about the length.
- **The single worst 3D bug was a missing `>> LGAME_FP_SHIFT`, and it produced an empty picture, not a skewed one.** `lgame_3d_project` cast `lgame_fp_div(...)` straight to `int`; that function returns 16.16, so every screen coordinate came out 65536x too large, every bounding box landed off-surface, and the rasteriser returned without drawing a single pixel. `drawn=0` with `submitted=13` is the entire signature. **Counters exist for exactly this**: "nothing was drawn" and "everything was culled or clipped" are different bugs with the same picture, and only the counters separate them.
- **Distances must be scaled before they meet a 16.16 coordinate.** The probe's first draft computed `z = FP_4 - (lgame_fp_t)d` with `d` a plain `int`, putting every quad at `z = 4 - 1` instead of `4 - 1.0`; view-space z then collapsed to ~1 and the near clipper rejected all 13 triangles. The tell was `vz=(1,1,1)` in the debug print. A host-side model of the same arithmetic disagreed with the kernel here — and the model was right, so bisect "is the kernel wrong or is my expectation of it wrong" before editing the kernel.
- **An edit that lands next to a behaviour change is not a cause — and here the evidence said so, if it was read.** Adding a debug `kprintf` to `lgame_3d_clear` coincided with the sky vanishing from the frame, which looked like proof that a serial print can perturb the render. Removing the print did **not** bring the sky back, so it was never the cause; the real cause was the missing shift above. Write the conclusion the revert-and-rerun actually supports, not the first correlation that appears. What did work was reading the framebuffer back from the kernel: after `lgame_present()`, sample `fb_get_active_buffer()` + `fb_get_pitch()/4` and print the packed values, which distinguishes "the writes never landed" from "they landed and were overwritten" in one boot. Also remember which frame you are reading — `/tmp/lgame.ppm` is whichever frame was captured **last** (post-quit, all black), `/tmp/lgame-<game>.png` is the in-game frame, and pairing one run's PNG with another run's PPM is meaningless.
- **`fb_backbuffer_end()` clears the back buffer to 0 after blitting.** Anything that draws "after present" is writing into a buffer that will be overwritten, and a screendump then shows the frame's own backdrop colour where geometry should be (for the selftest that is `lgame_clear()`'s `rgb(0,0,255)`). Combined with the missing shift above, that produced a viewport full of exactly the backdrop colour — the clearest possible symptom, easy to misread as "the clear never ran".
- **The depth staircase is drawn NEAREST FIRST on purpose.** Four nested quads, submitted blue→cyan→green→red, so every later quad overlaps every earlier one and the last one drawn (red) is also the largest. With no depth test, red simply covers the lot and all four samples read red. That makes one assertion set cover the entire depth buffer, and the ring widths are not arbitrary: the measured areas reconcile *exactly* with the hand-derived projection (red 40680, green 14265, cyan 10215, blue 8281 px), which is what proves the projection rather than just proving that four colours exist.
- **Arithmetic shift on a negative 16.16 value floors, so quads are not symmetric.** C's `/` truncates toward zero but `>>` floors, so `cx - 135` and `cx + 135` can differ by a pixel (cyan measured 136 wide, not 135). Do not write assertions that assume a screen rect is an exact square; derive the expected extents by running the same integer chain.
- **Probe C pairs a culled and a kept quad of *different sizes* in one frame, and the size difference is load-bearing.** If both quads were identical, a culler that silently ignored the winding would still hide the wrong-coloured one under the right-coloured one, and a "this colour must appear nowhere" assertion would pass for the wrong reason. Different sizes means a broken culler leaves a visible 17px ring (measured 4624 px) instead. The forward-wound quad is also the control that rules out a rasteriser which drew nothing at all — a lone "nothing here" assertion is equally satisfied by that.
- **The check parses the probe spec off the serial log instead of hardcoding a second copy of the geometry.** The kernel prints what it *intended* to draw (`lgame: 3dprobe <name> <x>,<y> <r>,<g>,<b>`, plus `sky`, `absent` and `3dcounters`); `parse_3d_spec()` reads it and a missing spec is a **failure**, because a check that cannot judge its subject must say so. A projection that puts a vertex in the wrong place then cannot make both the intent and the pixels agree, and the numbers cannot drift from the code that uses them.
- **Sample points sit >=12px inside their target and outside the next shape**, against on-screen half-extents of 135/90/67/45 px (offsets 112/78/55/30). That margin is what makes the assertions immune to the couple of units of fixed-point truncation in the projection.
- **The negative controls are `lgame_3d_break`, and `volatile` is the whole point of it being a variable.** Values 1–4 disable the depth test, culling, near-plane clipping and `lgame_3d_clear()` respectively. Written as `if (0)` or with a plain `int`, `-O2` reads it once, sees 0 and deletes the branch — a control that does nothing, leaving the assertion "passing" with the feature still broken. `x86_64-elf-objdump -dr pkgs/core/panels/src/lgame.o | grep -c lgame_3d_break` must show **4**; that count, plus the relink, is how a control is shown to have taken effect rather than assumed. Observed, all four FAIL and none fails for a reason other than the one it targets: 1 → the three nearer staircase samples read red; 2 → magenta appears over 4624 px *and* `culled=0`; 3 → the clip band reads sky and `drawn` falls 12→10 as the two fan triangles vanish; 4 → the sky check **alone** fires, with `drawn` still 12 — the quads are drawn over the unpainted background and their own samples still read correctly, so the sky is the only thing a missing clear takes away. Always run a `break=0` **baseline** alongside, since a control that behaves identically to the baseline is a control that did nothing.
- **Flat shading is a unit test of the shading term, and the probe says so.** `lgame_3d_tri_shaded()` takes the normal as an argument, so probe D passes three different normals to three coplanar quads. What is under test is that facing alone picks the brightness; calling it a lit scene would be a claim the geometry does not support. Expected values are derived from the documented formula, not read off a working build: light +Z, ambient 1/4, base `0xFFFF8000` gives `255/128/0` (lam 1.0), `198/99/0` (lam 46341/65536) and `63/32/0` (lam clamps to 0). The channels are deliberately asymmetric so a channel-order slip cannot hide behind three equal numbers. Control 5 forces `lam = 1.0`, and only `shade_mid`/`shade_dark` fail — `shade_lit` still passes, because the lit face's expected value *is* the base colour. A control that turns up nothing is not a control; this one was expected to leave one probe green.
- **Probe D cost two builds on a units bug that read as a shading bug.** The table stored screen offsets (+-108 px) and the geometry used them as world coordinates, so all three quads collapsed onto x=0 and the depth test rejected the second and third as exactly as near as the first. The symptom was "shading does nothing" — the lit colour everywhere — which points at the shading term rather than at the geometry. Scaling that constant a second time, instead of fixing the table, kept two probes failing. When several expected values come out as one value, suspect the geometry before the arithmetic.
- **The 3D viewport is 320x480 with a 16-bit depth buffer — about 300 KB.** It is deliberately smaller than the 1280x800 surface because a software rasteriser pays per pixel, and `selftest_3d()` calls `lgame_3d_end()` as soon as the probe is drawn rather than holding the buffer for the life of the frame. If `lgame_3d_begin()` fails to allocate, the selftest **returns a distinct negative rc** (`-31`), so "the probe could not run" can never be mistaken for "the probe passed".
